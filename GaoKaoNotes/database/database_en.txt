				🤔. Common applications: OLAP (Online Analytical Processing), big-data processing, and geographically distributed applications.

## 3. Basic Database Design Process
	A. Requirements Analysis
		a. Collect and analyze user requirements.
		b. Determine the types, scope, and size of the data.
		c. Define requirements for data integrity, consistency, and security.
	B. Conceptual Design
		a. Create an Entity-Relationship Diagram (ERD).
		b. Determine constraints among entities, attributes, and relationships.
		c. Design data normalization and denormalization.
	C. Logical Model
		a. Create relational schemas.
		b. Define primary keys, foreign keys, and indexes.
		c. Design data integrity constraints.
	D. Physical Model
		a. Select a database management system (e.g., MySQL, Oracle).
		b. Create tables, views, and indexes.
		c. Design data storage and query strategies.
	E. Implementation and Testing
		a. Import data.
		b. Perform functional and performance testing.
		c. Ensure data consistency and security.

	A. Chen's Notation (concepts that are easy to forget or confuse)
		a. Weak Entity
			I. A weak entity must depend on another entity to exist. For example, in a student database, a "Student Parent" entity depends on the "Student" entity. If Student A is removed from the database, Student A's parent entity naturally no longer exists.
			II. Represented by a double rectangle (an outer border).
		b. Weak Relationship: The relationship between an entity and a weak entity is represented by a double diamond (an outer border); an ordinary relationship uses a normal diamond.

		c. "Derived Attribute" means an attribute that can be derived from other attributes. For example, a zodiac sign can be derived from a person's date of birth. A derived attribute is represented by a "dashed ellipse."

		d. "Multivalued Attribute" means an attribute that can have multiple values, such as a skill attribute that can contain several skills. A multivalued attribute is represented by a "double ellipse."

		e. "Total Participation" and "Partial Participation"
		reference:
		https://faculty.stust.edu.tw/~jehuang/oracle/ch2/2-1.htm
			I. Suppose entities A and B have a relationship R. If every instance of A must participate in R, then A has **total participation** in R, represented by a double line. If an instance does not have to participate in R, it has **partial participation**, represented by a single line. The same applies to B.
			II. A weak entity C must depend on an entity D. In their relationship R, C must have total participation in R (while D does not necessarily have total participation). Therefore, in an ER diagram, a weak entity has at least one double line, and this double line points to the identifying relationship connecting it to its "owner" entity.

## 4. Database Design
	A. Normalization
	reference:
	https://stackoverflow.com/questions/723998/what-are-database-normal-forms-and-can-you-give-examples/724032#724032
		a. First Normal Form (1NF): Split fields that can be split, and do not have repeating data; in other words, a primary key is needed.
			I. Every non-key attribute should be dependent on the key.
		b. Second Normal Form (2NF): Attributes that are only partially dependent on the primary key must be separated.
			I. Every non-key attribute should be dependent on the key and the whole key.
		c. Third Normal Form (3NF): If an attribute is not directly dependent on the primary key, but depends on another attribute that is fully dependent on the primary key, that attribute should also be separated.
			I. Every non-key attribute should be dependent on the key, the whole key, and nothing but the key.
		d. BCNF ---> Every attribute (including non-key and key attributes) should be dependent on the key, the whole key, and nothing but the key.
		reference:
		The following explanation has an excellent example:
		https://www.youtube.com/watch?v=VWnKUKH4tLg
		Another explanation, but not very good (the example has problems!):
		https://stackoverflow.com/questions/8437957/difference-between-3nf-and-bcnf-in-simple-terms-must-be-able-to-explain-to-an-8

			I. "Candidate Keys" ---- A set of attributes that can uniquely determine a record (there may be multiple candidate keys). Candidate keys do not contain redundant attributes; candidate keys are a subset of superkeys.
			II. "Superkeys" ---- A set of attributes that can uniquely determine a record (there may be many); redundant attributes are allowed.
			III. "Functional Dependency" ---- Y depends on X, written as X -> Y. Remember! X -> Y means that once X is determined, Y is also determined. It does NOT mean that when X changes, Y must change! For example, a person's name depends on their ID number: once the ID number is determined, the name is determined. You cannot have ID = 1 and then have the name be either Wang or Mei; that would mean the name does not depend on the ID. I previously thought X -> Y meant "whenever X changes, Y must also change." That understanding is completely wrong!!! For example, different ID numbers can still belong to people with the same name. People can have the same full name. Therefore, that interpretation of dependency is incorrect!!!
			IIII. "Closure" ---- This is also a set-theoretic concept. Suppose the elements of a set S remain within the set after an operation F; then S is closed under F. If S is not closed under an operation, we can usually find the smallest closed set containing S. This smallest closed set is called the closure of S (with respect to the operation).

		e. Fourth Normal Form (4NF): "BCNF + remove all multivalued dependencies (MVDs)" ----> Multivalued dependency: In a relation R with at least three attributes, R(A,B,C), where the primary key is ABC, A corresponds to multiple values of B, A corresponds to multiple values of C, and B and C are independent.
		The following explanation is very good. Its example of a relation satisfying BCNF but not 4NF is particularly useful:
		https://en.wikipedia.org/wiki/Fourth_normal_form

		e. Finding Candidate Keys when Functional Dependencies are Known (remember: candidate keys are minimal subsets of superkeys; there may be many candidate keys. We can find superkeys and then identify the candidate keys)
			🤔. Question 1:
				R = {A, B, C, D, E}, functional dependencies: A->B, ED->A, BC->E. Candidate keys are {A, C, D}, {B, C, D}, {C, D, E}.

				Solution:
					The idea is simple if we proceed step by step.
					First, find all superkeys without considering dependencies (which is only R itself):
					{A, B, C, D, E}
					Then find superkeys considering one dependency at a time:
					{A, C, D, E} (remove B because A->B; B depends on A)
					{B, C, D, E} (remove A because ED->A; A depends on ED)
					{A, B, C, D} (remove E because BC->E; E depends on BC)
					Then consider one additional dependency based on the results above:
					{C, D, E} (starting from {A, C, D, E}, consider ED->A)
					{B, C, D} (starting from {B, C, D, E}, consider BC->E)
					{A, C, D} (starting from {A, B, C, D}, consider A->B)
					No more attributes can be removed according to the dependencies. Therefore the superkeys are:
					{A, B, C, D, E}, {A, C, D, E}, {B, C, D, E}, {A, B, C, D}, {C, D, E}, {B, C, D}, {A, C, D}
					The candidate keys are the minimal subsets:
					{C, D, E}, {B, C, D}, {A, C, D}

			🤔. Question 2:
				R = {A, B, C, D}, functional dependencies: D->B, AB->D, AB->C, C->A. Candidate keys are {C, D}, {A, B}, {B, C}, {A, D}.

				Solution:
					Use exactly the same method as in the previous question to find all superkeys:
					{A, B, C, D}
					{A, C, D} (according to D->B)
					{A, B, C} (according to AB->D)
					{A, B, D} (according to AB->C)
					{B, C, D} (according to C->A)
					{C, D} (according to D->B, C->A)
					{A, B} (according to AB->D, AB->C)
					{B, C} (according to AB->D, C->A)
					{A, D} (according to AB->C, D->B)
					{A, B} (according to AB->C, AB->D)
					{C, D} (according to C->A, D->B)
					After removing duplicates, the candidate keys are:
					{C, D}, {A, B}, {B, C}, {A, D}

		f. Decomposition
			I. When decomposing a table, we want a **lossless join**, meaning that joining the decomposed tables does not lose any data. A lossless join is achieved when "when one table is decomposed into two tables, their common attributes form the primary key of at least one of the two tables!" (This is essentially the intuitive way decomposition is usually performed.) Lossless join can preserve data integrity, reduce data redundancy, prevent update anomalies, improve query performance, and enhance data independence.

	B. Index
		a. Basic explanation: Why can an index increase search speed? It is not difficult to understand. If data is stored in a database without any data structure, searching uses linear search, with time complexity O(n). If a B-Tree (balanced m-way search tree) index structure is used, the search complexity naturally improves to O(log(n)).

		b. Disadvantage: Although indexes improve search efficiency, INSERT and UPDATE operations become slower because the index structure also needs to be maintained. Without an index, data can simply be inserted without worrying about maintaining the index structure.

		c. Clustered Index, Non-clustered Index
		reference:
		https://www.youtube.com/watch?v=YuRO9-rOgv4
			I. To understand the difference, we first need to know about B+ trees. Most database indexes actually use B+ trees (the B-Tree mentioned earlier was mainly for explanation; technically, B+ tree is more appropriate). B+ trees reduce tree height (improving search efficiency) by storing values in leaf nodes while other nodes store keys.
			II. The ordering of a clustered index corresponds to the actual physical ordering of the data, whereas the ordering of a non-clustered index does not and cannot determine the physical ordering of the actual data. Therefore, a table can contain many non-clustered indexes but only one clustered index.
			III. Clustered indexes make insertion slower but queries faster; non-clustered indexes make insertion faster but queries slower (although both are faster than having no index).

	A. ACID (Atomicity, Consistency, Isolation, Durability)
	reference:
	https://lance.coderbridge.io/2021/04/24/short-what-is-acid/

		a. Atomicity
			I. A transaction is the smallest unit and cannot be further divided. Operations within a transaction either all succeed or all fail.
		b. Consistency
			I. The operations of a transaction must be consistent with the rules of the real world.
		c. Isolation
			I. Transactions are independent of each other and do not interfere with one another.
		d. Durability
			I. After a transaction commits, its results should be persistent.

	B. Transaction Execution:
		a. Conceptually, a transaction consists of several of the following five basic operations:
			I. begin(T): indicates that transaction T begins execution.
			II. read(X, x): reads data item X from disk into main-memory variable x.
			III. write(x, X): writes main-memory variable x to disk data item X.
			IV. commit(T): indicates that transaction T successfully ends.
			V. abort(T): indicates that transaction T is rejected; all previous actions are rolled back.

	C. Concurrent Transaction Processing (usually used for efficiency; transactions are not executed strictly in sequence)
		a. Arbitrary interleaving (concurrency): If the same data is accessed, the following problems may occur:
			I. The Lost Update Problem
			II. The Dirty Read Problem
			III. The Non-repeatable Read Problem
			IV. The Phantom Problem
			V. To avoid the above problems, transaction isolation is required.

	D. Checkpoint Mechanism:
	reference:
	https://www.newton.com.tw/wiki/CheckPoint
	http://debussy.im.nuu.edu.tw/sjchen/Database/Final/Ch09.pdf
		1. commit (regardless of which transaction commits) writes the current history_log in the cache, including logs from all transactions, to the history_log on disk. A checkpoint writes both cached data and the cached history_log to disk. Therefore, a checkpoint updates both the disk history_log and the disk data area. Note that every database operation (insert, delete, query, update) affects data in the cache but does not affect the disk data area; only a checkpoint writes cached data to the disk data area.
		2. When a crash occurs, the database system checks the disk history_log. If T1 has action records after the checkpoint and eventually committed, the system performs redo() for T1's actions after the checkpoint. If T2 has actions after the checkpoint but never committed, the system performs undo() for all of T2's actions recorded in the entire disk history_log, even if some of T2's actions occurred before the checkpoint. This is effectively equivalent to aborting T2. Remember that redo() and undo() operations are themselves recorded in the cached history_log, and when a new commit() occurs later, these undo() and redo() operations are also written to the disk history_log. Furthermore, undo() and redo() operate on the disk data area.

	E. Isolation Levels ----> Used to solve problems that may occur during concurrent transaction processing
		a. Read Uncommitted
			I. Allows a transaction to read changes made by other uncommitted transactions.
			II. Possible problems: Dirty Read, Non-repeatable Read, Phantom Read.
			III. Advantage: Best performance and lowest overhead.
			IV. Suitable for scenarios with relatively low consistency requirements.
		b. Read Committed
			I. Can only read changes committed by other transactions, preventing dirty reads.
			II. Possible problems: Non-repeatable Read, Phantom Read.
			III. Advantage: Good performance with relatively low overhead.
			IV. Suitable for most applications with moderate consistency requirements.
		c. Repeatable Read
			I. Within the same transaction, repeated reads of the same data are guaranteed to be consistent, preventing non-repeatable reads.
			II. Possible problem: Phantom Read.
			III. Advantage: Higher isolation with moderate performance overhead.
			IV. Suitable for systems such as banking systems that require relatively high data consistency.
		d. Serializable
			I. Provides the highest isolation level and ensures transactions execute in a serializable manner, avoiding dirty reads, non-repeatable reads, and phantom reads.
			II. Possible problem: Strict isolation may cause more transaction conflicts and lock contention, resulting in the highest performance overhead.
			III. Advantage: Strongest data consistency guarantee.
			IV. Suitable for applications requiring the highest consistency, such as financial transaction systems.

	F. Two-Phase Locking Protocol (2PL) ----> A common concurrency-control protocol used to ensure serializability. It has two phases:
	reference:
	https://zhuanlan.zhihu.com/p/133823461
	https://www.twblogs.net/a/5d407451bd9eee51fbf99a58
	https://www.itread01.com/articles/1476768602.html
		a. Basic definition:
			I. Within "!!!!!!ONE transaction (look at only one transaction, do not consider many transactions together)!!!!!!!", there is a lock phase and an unlock phase; all lock operations occur before unlock operations.
		b. Basic content:
			I. Growing Phase:
				🤔. During this phase, a transaction can acquire locks (read locks and write locks), but cannot release any lock.
				🤔. When a transaction needs to access a data item, it must first acquire the corresponding lock.
			II. Shrinking Phase:
				🤔. During this phase, a transaction can only release locks and cannot acquire new locks.
				🤔. Once the transaction releases its first lock, it enters the shrinking phase.

		c. Problems that may occur with 2PL:
			I. If, in a transaction T1, I unlock a resource before committing (which is allowed under basic 2PL as long as all unlocking happens together), and then later abort T1, another transaction T2 may lock and access that resource between T1's unlock and abort. T2 may not know that T1 has aborted and may read a result that should not exist. This causes an error. Therefore, in practice, **Strict Two-Phase Locking (S2PL)** is commonly used.

	F-2. Strict Two-Phase Locking (Strict 2PL)
		a. Basic definition:
			I. Within a transaction, the unlocking phase occurs only at COMMIT or ROLLBACK (ABORT).
		 b. Basic locking mechanism
			I. Every data item has an associated lock, with three possible states:
				🤔. SHARED_LOCKED: Before reading a data item ---> readable, not writable
				🤔. EXCLUSIVE_LOCKED: Before writing a data item ---> neither readable nor writable
				🤔. UNLOCKED: After processing the data item ---> readable and writable
			II. Follow the basic locking mechanism:
				🤔. After an operation is completed, the corresponding lock is not released immediately; all locks are released together only at COMMIT or ABORT.

	G. Deadlock ----> A problematic condition that may occur under 2PL or Strict 2PL
		a. Conditions:
			I. Mutual Exclusion:
				🤔. A resource can be used by only one process at a time.

			II. Hold and Wait:
				🤔. A process holds at least one resource while waiting for resources held by other processes.

			III. No Preemption:
				🤔. A resource can only be released voluntarily by the process; it cannot be forcibly taken away.

			IIII. Circular Wait:
				🤔. Each process waits for a resource held by another process (e.g., P1 waits for P2, P2 waits for P3, P3 waits for P1). This also means a single process cannot have a deadlock.

		b. Example:
			I. Alice needs resources x and y; Bob also needs x and y.
			II. Alice locks x; Bob locks y.
			III. Alice waits for y to be unlocked.
			IIII. Bob waits for x to be unlocked.

		c. Solutions (in operating systems):
			reference:
			https://ithelp.ithome.com.tw/articles/10206472

			I. Prevention
				🤔. Thoroughly consider possible deadlocks during program design and prevent them by design; this can be complicated.
			II. Avoidance
				🤔. Resource-Allocation Graph (RAG) algorithm
					😄. Use when each resource type has only one instance.
				🤔. Banker's Algorithm
					😄. Use when resource types may have multiple instances.
			III. Detection: Allow deadlocks to occur, but detect and recover from them.
				🤔. Single instance:
					😄. Use the wait-for graph algorithm (similar to RAG).
				🤔. Several instances:
					🤔. Use a detection algorithm.
			IIII. Ignore
				🤔. When a deadlock occurs, the system directly interrupts a process.
				🤔. Many operating systems use this approach because the first three methods consume resources, while directly interrupting a process may be more practical.

		d. Solutions (in databases; very similar to operating systems):
			I. Deadlock detection and rollback:
				🤔. The DBMS periodically checks for deadlocks and rolls back one transaction to resolve the deadlock.
			II. Deadlock timeout:
				🤔. Set a timeout period; if a transaction remains deadlocked beyond that time, automatically terminate one transaction.
			III. Optimize the database and queries:
				🤔. Use reasonable database design, optimize indexes, and reduce the time transactions hold locks.
			IIII. Use locking mechanisms:
				🤔. Use the locking mechanisms provided by the DBMS to manually manage concurrent access among transactions and avoid deadlocks.
			IIIII. Adjust the transaction isolation level:
				🤔. Lower the transaction isolation level from Serializable to Repeatable Read or Read Committed.
			IIIIII. Pay attention to transaction ordering when writing application programs.

SAN uses technologies such as Fibre Channel andCSI to provide high-bandwidth and low-latency data transmission. Although SAN is an independent network, it is usually integrated with an organization's LAN and WAN through servers to form an overall storage solution.

				🤔. Fast but expensive.
				🤔. It is not based on Ethernet (nor TCP/IP); it is an independent protocol and is not part of the OSI model.

			II.I (Small Computer System Interface):
				🤔. SCSI is an independent layered system that does not rely on traditional network protocol stacks such as MAC, IP, or TCP. It has its own layered structure and command set (independent of the seven-layer OSI model).
				🤔. Storage devices such as hard disks have different read/write requirements from ordinary computers, so a specialized protocol was needed to make storage access more efficient; SCSI was created for this purpose.
				🤔. Used for connection aa transfer between computers and storage devices.

		b. Advantages:
			I. High Scalability: SAN allows storage capacity to be expanded easily by directly adding storage devices without major changes to the existing architecture.
			II. High Fault Tolerance: SANs often use RAID (such as RAID 1 mirroring and RAID 5 parity), providing data mirroring, redundancy, recovery, and backup capabilities.
			III. High Performance: SAN networks use high-bandwidth, low-latency technologies such as Fibre Channel. Fibre Channel Protocol (FCP) transports SCSI commands over Fibre Channel networks, providing fast data transfer suitable for HPC and big-data processing.

		c. Disadvantages:
			I. High Cost: SAN hardware (such as Fibre Channel switches and storage devices), management software, and maintenance are expensive, making SAN more suitable for large enterprises and organizations requiring high-performance storage solutions.

	E. IP-SAN
		a. Basic definition: Its architectural concept is the same as SAN, but instead of using Fibre Channel protocols, it uses TCP/IP to transmit data. This greatly reduces deployment and management costs, although performance is generally lower. It uses the iSCSI protocol (FC-SAN uses Fibre Channel and SCSI).
			I. iSCSI (Internet Small Computer System Interface)
				🤔. iSCSI is a protocol that encapsulates SCSI commands in TCP/IP packets and transmits them over standard Ethernet.
				🤔. In IP-SAN, storage devices and servers exchange SCSI commands and data through Ethernet.
				🤔. IP k devices such as Ethernet switches, routers, and standard network interface cards (NICs) form a storage network using TCP/IP.

		b. Advantages:
			I. Low Cost: Provides the basic advantages of FC-SAN while using existing Ethernet infrastructure, reducing hardware and maintenance costs.
			II. Flexibility: Uses standard network equipment and is easy to expand and manage.
			III. Broad Compatibility: Supports remote storage access and data backup through WANs.

		c. Disadvantages:
			I. Lower Performance: Although modern Ethernet (such as 10-Gigabit Ethernet) is very fast, it may still be inferior to Fibre Channel in some high-performance applications.
			II. Network Contention: Shares bandwidth with other network traffic, which may cause congestion and performance degradation.
